## 关一 · 真实（它说的问题，代码里到底有没有）

### 1. 文件、函数、变量、配置项存不存在

```bash
# 全仓搜（跳过 node_modules / dist / .git）
rg -n "函数名|变量名" -g '!node_modules' -g '!dist' -g '!.git'

# 只在某类文件里搜
rg -n "useEffect" -t ts
```

搜不到 → 再搜同义词、旧名字、驼峰/下划线变体，确认不是改名了。

### 2. 行号对不对

```bash
# 直接看那几行
sed -n '38,46p' src/hooks/useSync.ts

# 用脚本一次验完（推荐）
python3 scripts/check_refs.py 审查报告.md --root .
```

### 3. 那一行是什么时候变的（判断"意见过时"还是"幻觉"）

```bash
git blame -L 41,41 src/hooks/useSync.ts
git log -L 41,41:src/hooks/useSync.ts --oneline | head -20
git log -S "旧函数名" --oneline | head        # 这个字符串哪次提交加/删的
```

**结论怎么写**：

| 情况 | 结论 |
|---|---|
| 行号对、内容一致 | 问题真实存在 → 进关二 |
| 行号偏了几行、内容还是那段 | 问题真实，位置要按现在的写 |
| 那行三个月前就改了 | **意见过时**，理由写"该写法已在 `<hash>` 改掉" |
| 全仓搜不到 | **幻觉**，理由写"仓库里没有这个东西" |

### 4. 它说的"行为"能不能复现

- "会内存泄漏" → 看有没有 removeEventListener／clearInterval／取消订阅
- "没有鉴权" → 顺着路由 → 中间件 → 处理函数走一遍，看鉴权在哪一层
- "会 N+1 查询" → 看循环里有没有查库
- "并发不安全" → 看有没有共享可变状态、锁、事务

★ **它说的"缺失"，先确认不是在别处做了**（装饰器、中间件、基类、全局拦截器）。这是误报重灾区。

## 关二 · 依据（它凭什么这么说）

### 1. 版本

```bash
# Node / 前端
cat package.json | head -40
npm ls react react-dom --depth=0

# Python
grep -A20 "dependencies" pyproject.toml
pip show fastapi | head -3

# Go
head -20 go.mod

# Rust
grep -A10 "\[dependencies\]" Cargo.toml
```

**核对**：它建议的 API／配置项，在当前版本里有吗？哪个版本引入的？哪个版本废弃的？

### 2. 官方文档

- 去官网／GitHub README／CHANGELOG 查，**不查二手博客、不查 AI 摘要**
- 看文档左上角的版本号对不对得上项目
- 查不到 → 记"未核到"，不引

### 3. 规范与安全清单

- RFC／W3C／MDN：条款号要对得上
- OWASP Top 10／Cheat Sheet：看具体条目，别只看标题
- 安全类意见**必须看数据流**：用户输入从哪进、经过哪、到哪去

### 4. "业界做法"

说"大家都这么写""最佳实践"的，多半没有硬依据——**只能算建议，不能算问题**。归到"要你定"或"不采纳（风格偏好）"。

## 关三 · 契合（符合这个项目吗）

### 1. 项目约定

```bash
ls AGENTS.md CLAUDE.md CONTRIBUTING.md README.md .editorconfig 2>/dev/null
cat .editorconfig 2>/dev/null | head -20
```

有 `AGENTS.md`／`CLAUDE.md` 的，**通读一遍**——里面常写着"不许改哪些文件""提交前跑什么""目录怎么分"。

### 2. 现有做法是什么

```bash
# 找同类实现，看仓库里是怎么写的
rg -l "同类模式关键词" src/ | head
rg -n "export function .*Service" src/ | head    # 例：看服务层怎么组织
```

**它建议的写法，跟仓库里其他 20 处都不一样 → 违约定。**

### 3. 破坏兼容

```bash
# 改函数/组件，先数调用方
rg -n "函数名\(" -g '!node_modules' | wc -l
rg -n "from ['\"].*模块名['\"]" | wc -l

# 改数据库 schema / 配置格式，看有没有迁移目录、有没有外部使用者
ls migrations/ prisma/ alembic/ 2>/dev/null
```

### 4. 红线

- 密钥、token、证书怎么存的（有没有硬编码、有没有进 git 历史）
- 权限模型（谁能调哪个接口）
- 许可证（引入 GPL 依赖进闭源项目就是雷）
- 项目明确说"不许动"的文件

### 5. 过度设计

问三句：

1. **现在哪个调用方需要它？** 没有 → 过度
2. **有第二个实现吗？** 只有一个 → 抽象层多余
3. **是为将来预留的吗？** 是 → 记下来，不做

## 关四 · 代价（改了这一处，别处会不会塌）

| 问题 | 怎么查 |
|---|---|
| 改动面多大 | 数要改的文件数；超过 5 个就要单独说明 |
| 有没有测试兜底 | 看测试目录、看这个模块有没有测试文件；没有就先补测试再改 |
| 要不要加依赖 | 加包前问：标准库能不能做？现有依赖能不能做？包多大？维护活跃吗？ |
| 性能影响 | 要数据，不要"可能更快／更慢"；没有数据就写"未测" |
| 要不要迁移 | 数据／配置／用户数据；要迁移就要回滚方案 |
| 能不能回滚 | 一个 commit 能回退吗？有没有不可逆操作（删表、发消息、外部调用） |

**判定时记住一条**：**收益 ÷ 代价**。收益是"修掉一个真问题"，代价是"动 8 个文件 + 加 1 个依赖 + 没有测试"。代价大的，宁可记下来不做，写进"要你定"。
